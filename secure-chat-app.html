Purpose · trust · workflow

Private conversation without trusting the relay

Secure Chat demonstrates encrypted messaging without asking users to trust the relay with plaintext.

  1. Endpoints exchange public keys while private keys remain local.
  2. The sender protects an AES key with the recipient's RSA public key.
  3. The relay forwards ciphertext that only the recipient can verify and decrypt.
Boundary · protocol · cryptography

Hybrid encryption across isolated endpoints

Python clients combine RSA-OAEP key wrapping, AES-256-GCM payload encryption, and a framed TCP protocol behind a Tkinter workflow.

  1. Clients generate or load persistent RSA keypairs and exchange only public keys.
  2. AES-GCM provides message confidentiality, integrity, and tamper detection.
  3. Typed, length-prefixed frames keep socket transport deterministic.

Technical Implementation

Encryption Architecture

Cryptography, networking, framing, and UI state are separated into focused modules:

  1. Endpoints exchange public keys through the relay.
  2. The sender wraps an AES key with RSA-OAEP and encrypts the payload with AES-GCM.
  3. The recipient authenticates and decrypts the framed message locally.

Security Boundaries

Relay Boundary

The server sees connection and framing metadata, but message contents are encrypted before transport.

Identity Assumption

Public keys travel through the relay; a production version should require peer fingerprint confirmation.

Hardening Path

Peer verification, protected key storage, TLS, reconnect handling, and automated integration tests are the next upgrades.
