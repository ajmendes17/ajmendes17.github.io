Purpose · trust · workflow

Private conversation without trusting the relay

I built Secure Chat as an educational demonstration of how encrypted messaging works. The goal was not just to make messages unreadable to the server, but to show the process in a way that someone less technical could follow.

  1. Each person has a public lock and a private key.
  2. The sender uses the recipient's public lock to protect a temporary message key.
  3. The actual chat message is locked with that temporary key.
  4. The server only passes the locked package along.
  5. The recipient unlocks it locally with their private key.
Boundary · protocol · cryptography

Hybrid encryption across isolated endpoints

Secure Chat implements a hybrid-encryption flow in Python. Clients generate or load RSA keypairs, exchange public keys through a relay server, wrap a per-message/session symmetric key with RSA-OAEP, and encrypt message payloads with AES-256-GCM before transport.

  1. RSA-OAEP handles asymmetric key wrapping for the AES key.
  2. AES-GCM provides confidentiality and authentication for message payloads.
  3. A shared protocol frames message type and payload length for socket transport.
  4. The relay server coordinates clients and forwards ciphertext without decrypting content.
  5. The Tkinter UI exposes the chat workflow and key fingerprint context.

Overview

The Secure Chat Application is a complete educational demo of encrypted messaging. The server coordinates connections and relays packets, while clients handle key generation, key exchange, encryption, decryption, and the user-facing chat workflow.

It is intentionally small enough to inspect, but it still shows several real system concerns: binary message framing, persistent RSA keys, authenticated encryption, GUI state, and component-level test scripts.

Technical Implementation

Encryption Architecture

The application separates cryptography, networking, protocol framing, and UI work into focused modules. The typical message flow is:

  1. Each client loads or generates an RSA keypair.
  2. The server relays public keys between connected clients.
  3. A session key is generated and wrapped with RSA-OAEP.
  4. Messages are encrypted with AES-GCM and sent through the shared protocol.
  5. The recipient verifies and decrypts the ciphertext locally.

Security Boundaries

What the Server Can See

The relay server coordinates clients and forwards framed protocol messages, but chat contents are encrypted before they leave the client.

Message Integrity

AES-GCM gives each encrypted message an authentication check, so tampered ciphertext fails instead of silently decrypting into bad data.

Current Trust Assumption

Public keys are exchanged through the relay, so a production version would need peer fingerprint confirmation to reduce impersonation risk.

Demo Storage Tradeoff

Private keys are stored unencrypted for development convenience. A hardened version should protect them with a passphrase or OS key store.

Next Hardening Steps

TLS transport, reconnect handling, encrypted key storage, peer verification, and pytest automation are the clearest next upgrades.
